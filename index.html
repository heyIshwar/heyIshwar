Case study · personal project

Spear: a law-enforcement intelligence platform

A multi-tenant platform that turns time-critical phone and SMS investigation requests into one tracked, auditable workflow — with a field app, an SMS gateway and an AI assistant that keeps a human in charge.

Node.jsFastAPIMongoDBLanceDBReact + MUI Flutter / AndroidAgnoAWSCloudflare

Impact

Built and shipped for the Maharashtra Cyber Police at district level: officers no longer need night shifts to chase phone and location requests, and investigations move faster toward arrests.

The problem

Cyber cells work against the clock. Requests to telecom operators, case notes, location trails and reports live across phones, spreadsheets and messaging apps, so nothing is auditable and follow-ups slip. Spear replaces that with one system of record per police unit, without forcing officers to change how they already communicate.

Architecture

AI engineering

  • Multi-agent assistant. A router plus specialist agents (built on Agno) that answer questions about cases, requests and tenant knowledge instead of one do-everything prompt.
  • Human-in-the-loop by default. Actions with side effects need explicit officer approval; the assistant proposes, the officer decides.
  • RAG with data residency. Tenant knowledge is retrieved from the tenant's own store — including an on-prem option — so sensitive records don't need to leave the customer's boundary.
  • Two-loop evaluation. Online feedback plus offline regression runs continuously measure and improve agent accuracy in production. Models run through OpenRouter (Gemini Flash-class) on a LanceDB knowledge base.
  • Cost and quality controls. Per-tenant usage quotas with overage billing, admin dashboards, and LLM tracing to debug and evaluate agent runs.
  • Investigator toolkit. A registry of analysis tools with run history, plus a CDR analysis engine (Python) that links entities across records.

Web & platform engineering

  • Real-time relay. One Node.js process serves REST and Socket.IO; the Android gateway and the console stay in sync as requests move through their states.
  • Reliable SMS pipeline. Idempotent job claims, inbound de-duplication, dual-SIM operator routing and push keep-alive so jobs are neither lost nor sent twice.
  • Access model. System admin, tenant admin and officer roles, extended with a district command hierarchy and per-feature grants.
  • Field workflows. Patrol beats, rosters and proximity-verified check-ins in a Flutter app, with maps and reverse geocoding in the console.
  • Local-language UX. English, Marathi and Hindi across the console.

Security & compliance posture

  • India-region hosting; optional per-tenant on-prem database (bring-your-own-data).
  • Operations aligned with CERT-In directions — incident process, log retention, time sync.
  • DPDP-oriented design: clear separation of fiduciary and processor responsibilities, subprocessor transparency.
  • Architecture decisions recorded as numbered ADRs, so every trade-off is traceable.

Telecom & geospatial

  • Parsing pipelines for telecom records: IMEI vs IMEISV, Cell-ID / LBS resolution, azimuth derivation and TAC lookups.
  • Geofencing on district boundary data with Google Maps for suspect-tracing workflows.
  • Cross-collection join safety in MongoDB so multi-tenant data never leaks across units.

Delivery & operations

  • Two-environment release flow (development → production) with Slack deploy and infrastructure notifications.
  • Prometheus, Grafana and Loki dashboards; automated Mongo backups to S3.
  • Cypress end-to-end and API test suites; versioned release notes across relay, console and mobile apps.

My role

Sole builder — data model and APIs, web console, Android gateway and field app, AI agents, and self-hosted production infrastructure on AWS behind Cloudflare.

Customer names, data and infrastructure specifics are confidential and deliberately omitted. Happy to walk through the design in more depth in an interview.
